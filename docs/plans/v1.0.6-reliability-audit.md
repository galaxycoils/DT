# DT v1.0.6 reliability audit and repair plan

Audit baseline: 23 November 2026, commit `986ce3a134af2130f1af8e097aeba2ce4fdc35c8`. The release tag, GitHub default branch, and local checkout agreed. First protect user data during database opens and upgrades, and make hosted workspace selection fail closed. Then make the published upgrade path usable.

## What the release already proves

- The [tag CI](https://github.com/galaxycoils/DT/actions/runs/45238516309) passed on macOS, Windows, Ubuntu x64 and Ubuntu ARM64, including a separate PostgreSQL 16 job. The [publication workflow](https://github.com/galaxycoils/DT/actions/runs/45245938156) produced eight primary downloads and their checksums. The duplicate [master CI](https://github.com/galaxycoils/DT/actions/runs/45238516508) failed after two attempts to acquire a macOS runner. The second attempt’s annotation explicitly identifies hosted runner capacity.
- The original release validation ran the full local Rust suite with 424 passes and six skips. In this audit the Companion and React browser smoke passed using Brave, isolated daemon storage, and mock inference. It exercised authentication, persistent chat, reconnect, a sandboxed Page preview and sign-out. All three web tests, the mobile contract test and all eight release-tool tests passed again.
- Running `target/release/xtask certify all --allow-incomplete --json` reran the automated fixtures successfully. The report counted 28 required inventory rows and returned `evidence_required` for providers, native, UX, integrations, lifecycle and soak. No evidence directory was supplied. Green fixture, build and export results cover only their exercised paths.

## Findings and acceptance tests

| Priority | Finding and evidence | Repair and test that closes it |
| --- | --- | --- |
| 1 | **A healthy store can enter recovery on an operational error.** In `gm-openbot/src/db_recovery.rs`, an open or quick-check error sets `is_healthy` to false. Queue, channels, chat, billing and other ordinary opens call this function. It can rename the database and then open a new file. This is a source finding with potential data impact. No user data loss was observed. | Separate confirmed corruption from busy, locked, permission and I/O errors. Reuse the existing storage lease and preservation logic where its behavior matches. Return an actionable error on ordinary opens. Test concurrent legitimate clients and interrupted explicit recovery in disposable profiles. Verify original rows, file identity, WAL data and backups after retry. |
| 1 | **Snapshot and restore disagree with Doctor on SQLite integrity.** A schema-v1 fixture with a healthy FTS5 table in `channels.sqlite` failed `dt doctor repair` while verifying its new snapshot. The error was “attempt to write a readonly database.” A nested `memory.sqlite/memory.db` fixture completed repair, but `migration.rs::is_sqlite_name` only recognizes two other extensions. The nested database goes through ordinary file copy. A concurrent-write consistency failure is a risk, not an observed loss. | Recognize the actual database layouts. Use a consistent SQLite snapshot for each database, handle its WAL/SHM as a unit, and reuse FTS-aware validation during migration and restore. Test flat and nested stores, committed WAL rows, corrupt indexes, disk-full and interrupted restore. Compare restored rows and FTS search results, including with a live reader. Preserve the existing conflict and pending outcomes. |
| 1 | **Hosted workspace selection can fall back to the default store.** Source review of the v1 middleware and `ActiveSupervisor` found that a workspace initialization error can be discarded and a default supervisor substituted. The consequences depend on the handler and deployment. | Make scoped workspace resolution mandatory for hosted data routes. Return an error if selection fails. Review the handlers that still take shared state directly. Test workspace creation, normal isolation and an unavailable worker store with two synthetic tenants. Require zero reads or writes to the default store on a failed hosted request. |
| 1 | **The published Apple Silicon updater cannot check for releases.** The executable extracted from the v1.0.6 installer returned “No pinned DT update publisher key” for `dt update --check --json`. The public metadata branch listed two JSON files, no signature files, and its DT metadata named v1.0.0. The CLI help also lists the old repository. | Build a new candidate with the publisher public key, produce and verify signatures for its exact six installer digests, publish matching metadata, and correct help text. Give existing v1.0.6 users a documented manual first upgrade. Exercise a subsequent signed update from the installed candidate. Check wrong-target, expired, altered and older metadata rejection. |
| 2 | **Local component installation and readiness disagree.** The installer writes versioned `payload.bin` files. The managed VLM loader expects a worker specification, executable and, for multimodal inference, projector weights. Doctor considers both Installed and Verified entries for readiness. The operations guide directs users to `dt models pull`, which calls a separate Candle registry. The normal component catalog loader also calls `parse_unverified`, although the guide describes signed catalog verification. | Reconcile the CLI, Settings, configuration-specific storage and runtime lookup. Define the supported trust path for bundled and external catalogs. Activate the complete worker package and matching model resources. Test a clean install, interrupted download, restart, failed verification and a real offline image-to-text request. Report the last successful startup or inference probe separately from file verification. |
| 2 | **Native voice can report success without audible playback.** The local HTTP TTS success branch in `gm-openbot/src/voice.rs::speak` returns `spoken: true` and a byte count, then drops the returned audio. The native UI has a handler for a transcribed response, but the composer actions inspected send start, consent, speak, barge-in and stop without a microphone-to-transcribe action. Doctor marks the combined voice capability Ready when STT alone is installed. These findings come from the source trace. | Wire consented microphone capture to the transcription request and decoded TTS audio to an output sink. Distinguish synthesis, playback and completion in status. Test fake input/output devices with a known phrase and audio frames, cancellation and consent revocation. Confirm audible playback and dictation into the intended draft on real hardware. |
| 2 | **Mobile workspace credentials and hosted bearer authentication disagree.** The mobile client sends a bearer token and workspace ID. In the v1 middleware the bearer branch first requires the configured operator token, so a separately provisioned workspace bearer cannot reach its workspace authorization check. This is a source finding. | Give mobile a scoped device credential or enrollment flow. Test provisioning, first connection, revocation and reconnect with a dedicated device identity. Reserve operator credentials for administration. |
| 2 | **Mobile can show stale or misleading results.** In `clients/mobile/app/routines.tsx`, selecting a new routine starts another history request. A late response for the first selection can replace the second selection’s runs. In `app/index.tsx`, channel and activity failures become empty lists. The existing mobile contract test mostly checks source strings and file presence. | Bind each result to the current selection and connection, cancel stale requests, and give each failed section a retry state. Test intentionally delayed responses, disconnect while loading, switch workspace, background/resume, and retry after an interrupted send. Verify rendered UI and persisted data on iOS and Android. |
| 2 | **Snapshot verification consumes memory in proportion to the largest file.** `migration.rs::sha256_file` reads the whole file into memory. On this Apple Silicon host, a repair of a disposable profile with one attachment peaked at 55.3 MiB RSS for a 1 MiB file and 118.5 MiB for a 64 MiB file. Both repairs succeeded. | Stream hashing through a fixed-size buffer. Compare digests byte for byte with the existing implementation and rerun the same fixtures plus a 1 GiB attachment. Record peak RSS and elapsed time. Require bounded hashing memory as file size grows. |
| 3 | **Doctor performance and snapshot wording need attention.** Median end-to-end `dt doctor check --json` across seven warm runs was 60.8 ms on an empty current-schema fixture and 103.9 ms with a 4.6 MB, 25,000-row FTS5 fixture. This is a local baseline. The FTS fallback copies the database and checks the copy. Also, `doctor snapshots` advertises verified snapshots but listing only parses manifests. Explicit inspection verifies size and hashes. | Measure Doctor on realistic large profiles with concurrent writers, including temporary space, before changing the fallback. Benchmark an upstream-compatible SQLite fix against the current behavior. Keep listing cheap and label its verification state accurately. Test an unreadable manifest, missing file and changed file. |
| 3 | **Release evidence and operator guidance have drifted.** The current README links to readiness notes headed v1.0.1. The v1.0.6 inventory still labels some installer builds pending even though the packages exist. The public macOS build uses ad hoc signing and Windows ships without Authenticode. The hosted quick start assumes the reader already has an enrollment token. | Publish a per-version matrix generated from release assets, CI and native evidence. Document the first operator’s workspace creation, enrollment and redemption steps. Test the instructions with a clean HTTPS deployment. Track runner allocation failures separately from failed assertions and preserve the successful tag run as release evidence. |

## Delivery sequence

1. **Storage and upgrade safety.** Start with ordinary opens, snapshot consistency and hosted isolation. Use the shared [storage implementation](../../crates/gm-core/src/database.rs), [snapshot code](../../crates/gm-daemon/src/migration.rs) and [Doctor regression](../../crates/gm-daemon/src/doctor.rs) as starting points. Make each regression fail on the baseline and pass after its fix. Run these tests on all three desktop OS families. Resolve the updater and complete a manual v1.0.6-to-candidate upgrade while preserving profiles.
2. **Complete the local features.** Close the model and voice findings, then test the shipped static Spaces, workspace guest, bundled skills and desktop controls on clean installs. For the guest, demonstrate a real boot, task, cancellation and patch review. For desktop controls, check real permission grant/revocation, helper restart, multi-display input and immediate stop. Preserve the existing chat-first UI.
3. **Verify each client against a real backing service.** Keep the existing browser smoke as a fast control. Add common user journeys across native, Companion, React and Expo wherever the feature is advertised. Cover DM/channel history across restart, approvals, routine trigger and run history, activity body, attachment, Page preview, provider setup, sign-out and reconnect. Exercise keyboard-only use, screen readers, narrow layouts, offline return, and two sessions editing concurrently. Run a separate fresh Docker Compose deployment with Caddy and PostgreSQL through workspace creation, enrollment, chat, revocation, backup and restore.
4. **Measure integrations and performance.** Exercise all eight provider rows from [the inventory](../release/coverage-inventory.json) through model discovery, one completed reply, cancellation, renewal and disconnect. Use local or sandbox services first for connectors, meetings, SIP, marketplace and billing. Record live-account tests separately with consent and the existing budget ledger. Measure startup-to-interactive, first reply, idle process-tree memory, capture/input latency, long transcript scrolling, SSE replay, and model cold/warm startup. Use the same hardware, fixtures and release settings before and after each optimization. Record at least 30 samples for latency gates and apply the repository's published budgets.
5. **Qualify the exact candidate.** Run locked workspace tests, lint, front-end typechecks, mobile exports, real browser smoke and PostgreSQL CI. Run clean install, upgrade from v1.0.5 and v1.0.6, interrupted upgrade, restore and uninstall against the packaged binaries. Cover macOS Intel/Apple Silicon, Windows x64/ARM64, Ubuntu x64/ARM64 on X11 and Wayland, plus iOS/Android client devices. Execute the repository's seven-day soak. Record the commit, package hash, environment, test result and evidence for every required inventory row. Use publisher identities and native runners for the signed candidate.

Release acceptance requires passing data-preservation and upgrade tests, executable coverage for every advertised critical journey, reviewed performance measurements, and a strict certification run with evidence for the same candidate. Keep remaining device, provider or hardware gaps visible by target and feature. These gates establish what was verified for a version and make future regressions detectable.
